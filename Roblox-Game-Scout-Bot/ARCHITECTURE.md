# Roblox Game Scout — Actual System Architecture

> This file is the **code-accurate** architecture reference. The older
> "System Architecture & Documentation" PDF describes an earlier/planned
> design (APScheduler, RoTrends discovery, a different SQLite schema, a
> `bot.py` entrypoint). Where the PDF and this file disagree, trust this
> file — it was written from the source code.

## What it is

A Python 3.11+ Discord bot (discord.py 2.x) that discovers Roblox games with
acquisition potential: it scans official Roblox APIs plus third-party
analytics sources, scores and filters games, posts alert embeds with
persistent buttons, tracks watched games for CCU/visit breakouts, and runs an
AI analyst over alert-worthy games. A companion portfolio worker/API serves
live stats for external dashboards.

## Runtime components (all in `Roblox-Game-Scout-Bot/`)

| Component | Module(s) | Reality |
| --- | --- | --- |
| Discord client | `main.py` | `discord.Client` + `CommandTree`; registers alert buttons as **DynamicItems** (regex custom-id templates — presses on pre-restart alerts still dispatch); answers cooldown rejections with a friendly ephemeral message; **does not** re-sync global slash commands on restart (Discord caches them ~1h). |
| Slash commands | `commands.py` | `/scan`, `/trending`, `/game`, `/analyze`, `/testai`, `/aiusage`, `/profile`, `/settings`, `/saved` (+`/watchlist` alias), `/watched`, `/unwatch`, `/ignored`, `/unignore`, `/scanping` (opt-in pings on discovery alerts), `/status` (dependency health), `/scanwindow` (schedule readout), `/scan-now` (force a scan), `/pulse` (instant local market read — movers, chart climbers, radar catches), `/scorecard` (grades its own alert calls from the bot's own snapshots — honest hit rate, zero network), `/dossier` (full single-game briefing: live state, snapshot history, charts, ledger, cached AI verdict + the deterministic Scout Read narrative — one Roblox request, fail-soft, no cost), `/compare` (side-by-side two-game comparison — one batch Roblox request, Scout Scores computed per column, fail-soft on unresolvable IDs), `/leaderboard` (top Scout Scores among actually-alerted games, 7d/30d/all-time — pure local read of `alerted_games.best_scout_score`, zero Roblox requests), `/radar` (ascent-radar diagnostics: the same candidates + coverage counters the minute tick computes, so a quiet radar can be told apart from a broken one without server logs), `/benchmark` (runs `scripts/bench_bulk_reads.py` in a subprocess against a throwaway synthetic store — in-process would momentarily redirect `database.DATABASE` mid-scan — output cached 10 min and posted raw, with a drift check comparing the measured per-phase speedups against the committed baseline: any phase below 25% of its committed ratio gets a ⚠️ line (naming the host it measured) ROUTED by two signals — **breadth** (which phases slid: every measured phase sliding together is one host-wide line pointing at the machine/shared path, never at one read path; one phase sliding while the others sit at baseline is the code-regression signature) and the recent record, counted in that host's OWN runs (sustained routes to "find and fix that read path", an isolated narrow dip routes to "rerun, suspect host noise") — and never to re-recording a live regression — a phase low for longer than the whole window in that host's OWN runs escalates to a STUCK alert that names the host (the fix is not holding) instead of repeating the first warning — the count is per host, so an interleaved healthy host cannot reset it; no committed baseline → clean post; and with more than one machine in the log the post ends with the SAME per-machine table /perfhistory shows — each host replayed to its last run, with evidence and verdict — because this run measured only one host and an alert on an idle machine would otherwise never reach the channel). Every bench run (CLI or /benchmark's subprocess) also appends a dated entry to `data/perf_history.jsonl` (runtime evidence, not a test fixture — upgrades from the old `tests/` location are migrated once automatically) with **host metadata** (python version + platform — ratios are self-relative per machine, so the trend check evaluates PER HOST PLATFORM: each 📈 line counts one host's OWN slice (≥ `HOST_MIN_SLICE` runs) and requires ≥60% of it below the committed floor — threshold ceil(share × slice), floor 2; the share is FITTED against an AR(1) cluster-noise model, not picked by hand — so a host switch can neither fake a trend by pooling hosts nor mask a regression behind another host's healthy entries; an unlabeled run contributes no evidence, it is reported as host unknown; and only the NEWEST run's host speaks a verdict — another host's still-open alert is printed once as an ℹ️ "separate alert, NOT this run's verdict" line naming both machines, which `route_of` ignores, so moving the runs to a healthy machine posts no action about the previous one), and also on the fitted window check — the window is each host's OWN last 10 runs (`TREND_WINDOW`, `host_window`; a shared window gave an interleaved host only half of one and evicted an idle host's record), so short transient noise stretches stay silent while a sustained regression fires (`drift_trend_lines`, pure math in the same script), and the alert clears once the fix's healthy runs age the lows out of that window (5 healthy runs at the fitted bar — measured by the S5 recovery probe), `/perfhistory` (READ-ONLY: prints the accumulated `data/perf_history.jsonl` trend — recent runs with python/platform per row, per-phase ratios marked ⚠️ below 25% of the committed baseline, a `hosts:` caveat line when the shown runs span OS families, a per-machine table (each host replayed up to its last run: last run, run count, the evidence — implicated phase and how many of its OWN recent runs were low, or the host-wide breadth — and that machine's own verdict) so a host that has not run since the runs moved elsewhere is not read as resolved, and the ROUTED ACTION for the latest logged run — the same ⚠️/📈 messages `/benchmark` would post, rebuilt from the file by `drift_warnings` + `drift_trend_lines` and labelled by `route_of` with what to do: fix the regressed read path / rerun, suspect host noise / rule out the host on a host-wide slide — so the read-only view gives the operator the same action instead of making them re-measure; `format_history` pure math, no bench run, no writes; /benchmark measures, /perfhistory reads), `/heatmap` (weekly discovery grid: alert volume per ISO week with average peak score, from the same store), `/tokencheck` (which env vars the host passed in, no secret values), `/testbuttons`, `/testtracker`, `/scoretest`, `/hello`, `/about`. The expensive ones are rate-guarded: `/scan` has a 5-min per-user cooldown plus a process-wide single-scan lock, `/analyze` a 1-min per-user cooldown. |
| Scheduler | `scheduler.py` | `discord.ext.tasks.loop` (NOT APScheduler — it is not a dependency). Scan loop every `SCAN_INTERVAL` minutes (default 30), only inside the ET active window (default 10 AM–9 PM daily): scan → enrich → **filter first** → AI only on alert-worthy games → post → run tracker. **Discovery priority is momentum-aware**: the Scout Score + growth base tier is promoted one step by a live velocity spike (numeric ratio AND "spiking" label, ≥1.5 required) or a ≥5 chart-position climb, and demoted one step by a genuinely declining 72h trend ("declining" label AND ratio <0.8) — both signals come from data the pipeline already computes. **Ascent Radar loop every `ASCENT_CHECK_INTERVAL_MINUTES` minutes (default 5, 24/7 — it reads local snapshots only): detects breakouts BETWEEN scan cycles** and posts an interim 🚀 alert (escalated to 🔥 "Ascent continues" for games already in the alerted_games ledger). **Weekly Ledger loop (hourly tick): gates on `LEDGER_WEEKDAY`/`LEDGER_HOUR_UTC`, keys the ISO year-week, and burns the week key only after a successful channel send** — restarts cannot double-post, a missed due day is caught up later in the same week, a failed send retries next tick. All loops wait for full Discord readiness before their first tick. A game is marked alerted only **after** its alert posts successfully — a failed send or unresolved channel retries next cycle instead of silently consuming the alert. `mark_alerted` also records the game's peak Scout Score (`best_scout_score`) and re-discovery count (`alert_count`), which feed `/leaderboard`. |
| Discovery | `data_collector.py`, `roblox_search.py`, `trending_sources.py`, `game_search.py` | All Roblox-native: keyword search via `apis.roblox.com/search-api/omni-search` (**the old `/v1/games/list` and `/v1/games/recommendations` endpoints were retired by Roblox — they now 404**), curated seeds, and the official Roblox Charts explore API. **RoTrends, RoMonitor Stats, Creator Exchange and BloxAtlas were all removed** — no site scraping, no third-party source. Every collected game is stamped with `on_charts` from this cycle's chart sorts, carries its position within each sort (`chart_rank` + `chart_appearances`), and the positions are written to `chart_positions` once per cycle. |
| Enrichment | `roblox_api_async.py`, `discord_lookup.py`, `history.py` | Batch details (50 IDs/request — the endpoint 400s from 60 up), votes/ratings and thumbnails (one request per 100 games), descriptions, creator info, Discord invite lookup, and growth over the window read from the bot's own `game_history` snapshots. The Discord lookup is description-only: Roblox's `social-links` endpoints now answer HTTP 401, so they were deleted along with the two requests per game they cost. Network work is async aiohttp behind a shared semaphore; the history read is a local indexed query. |
| Scoring | `scanner.py` (`calculate_scout_score`), `trend.py`, `velocity.py`, `developer_intelligence.py`, `chart_rank.py` | Scout Score 2.0: growth 0–30, momentum 0–25, new-release 0–15, like ratio 0–10, velocity 0–20 (the velocity indexer's 0–100 momentum score scaled into the component budget — previously the raw 0–100 value overflowed this component and inflated totals), **chart rank 0–10** (position on a Roblox chart + climb bonus, from the bot's own `chart_positions` store), developer history 0–20 (cached 24h); total capped at 100. |
| Filtering | `filters.py` | Two tiers, both enforced by `evaluate()`: **base** thresholds from the `ALERT_*` env (CCU floor, visit ceiling, growth, Discord requirement), then the caller's `/settings` profile, where every stored value overrides the base. All ten options filter for real — CCU ceiling, rating floor, Discord toggle, chart presence, genre and max age included. Analytics links never reject; they enrich. |
| Alerts | `embeds.py`, `buttons.py`, `priority.py` | Priority tiers high/medium/low; per-user `alert_level` gates mentions (`setting_rank` maps settings onto the priority scale — an early version looked the setting up in the priority table and crashed on the default `all`). The four alert buttons are `DynamicItem` subclasses: each custom id carries the game id (`alert_claim:12345`) and a class-level regex template matches it in any session, so presses work on alerts posted before a restart (the old single persistent view matched custom ids only exactly and every pre-restart press failed). Claim bookmarks the game; Accept bookmarks **and** tracks it; Reject hides it per user. |
| Auto-watch | `scheduler.py`, `database.py`, `tracker.py` | After a posted alert, the scheduler adds a system watch (`auto_watch_game`) owned by `AUTO_WATCH_USER_ID` (default 0 = the bot), so the tracker keeps reporting on the game after its one-time alert. The `AUTO_WATCH_MAX` cap prunes only `source='auto'` rows (oldest first), never a human's watch; `/unwatch` lifts both the caller's and the bot's watch. |
| Tracker | `tracker.py` | Groups watch rows by game (several users plus the bot's auto-watch can track the same game — one fetch and one alert per game per cycle, not per row); snapshot guard skips alerting until a real baseline exists; alerts on **growth** (≥ +20% CCU or ≥ +5% visits) *and* on **decline** (≤ −50% CCU or ≤ −30% visits — steeper by design so noise never reads as a collapse, with its own embed styling); tracked-window trend confirmation, read from the bot's own history (no extra network call); chart-rank context from the local store; system (`source='auto'`) watches post quietly and never @-mention. Snapshot writes are batched: the whole cycle's `watched_games` updates land in ONE connection + commit (`update_watched_game_snapshots_bulk`, was one fsync per watched game), flushed after the loop — the in-memory baseline the cycle already compared against is unaffected. Window growth for every watched game is now ONE bulk pass before the loop (`history.growth_summaries_bulk`; was one connection + query per game inside the loop despite the bulk reader already existing). |
| Pulse | `pulse.py` | The bot's own market read on demand. `/pulse` and the digest's pulse section call local, indexed selectors — top CCU movers over 24 h from `game_history` (with a 30-min freshness gate: a stale snapshot is never presented as current movement), games whose chart position improved between the two most recent distinct cycles from `chart_positions` (cycle-over-cycle, not within one cycle), and Ascent Radar's recent catches from `ascent_state`. Names resolve from the bot's own records (`alerted_games` first, then `watched_games`). Zero Roblox requests by construction. Renderers and the report composer are pure functions (data in → text out), so empty data renders an explicit quiet line, never a blank section; selector failures are logged and degrade, never crash the command or digest. The morning digest also carries a 🏁 **all-time Scout leaderboard section** from `top_alerted_by_scout_score` (injectable rows keep the digest's pure-function contract; fail-soft; an empty store renders no section). |
| Ascent Radar | `ascent.py` | Early-breakout watchdog between scan cycles: every `ASCENT_CHECK_INTERVAL_MINUTES` (default 5) it runs one local, indexed pass over the 24h `game_history` window and flags games whose freshest CCU reading is ≥ `ASCENT_SPIKE_RATIO` (2.0×) the average of their *other* readings AND ≥ `ASCENT_MIN_WINDOW_RISE_RATIO` (1.5×) the window's low — a discontinuity, not the top of a steady climb. Freshness is part of the definition: the newest reading must be younger than the interval + 15 min, so stale data is never replayed as a live climb. Posting is rate-guarded: a per-game `ASCENT_COOLDOWN_MINUTES` (45) cooldown stamped in `ascent_state` before the send attempt (so a misconfigured channel cannot queue a burst), a per-tick `ASCENT_MAX_ALERTS_PER_CYCLE` (5) cap sorted highest-spike-first, and `ASCENT_ENABLED=false` opt-out. A game already in `alerted_games` is **escalated** ("🔥 Ascent continues") rather than re-announced. Candidate name/ledger resolution (`resolve_names`) is set-based: ONE connection and at most two indexed queries serve the whole candidate batch (was: 1–2 queries per candidate per tick). `find_ascent_candidates(return_diagnostics=True)` also reports coverage — counts per skip reason (too-few-snapshots / below-CCU / zero-baseline / below-ratio / stale snapshot) — and each tick logs fired/qualified/coverage in one line, so a quiet radar can be distinguished from a broken one. Zero Roblox requests by construction. |
| Dossier | `dossier.py` | Single-game deep read behind `/dossier`. One Roblox request (`get_game_info`) for live state; everything else is local: window growth (`history.py`), 72 h momentum (`velocity.py`), chart positions + movement (`chart_rank.py`), the alert/watch/radar ledger (direct SQLite reads — human watchers counted, auto rows excluded), and the stored AI verdict from `ai_analysis_cache` (never triggers analysis). The **Scout Read** narrative is a deterministic rubric — momentum ratio / chart presence / window growth / network presence → 0–6 → 🔥/📈/🌱/⚪ bands with stated reasons — pure, free, and always available; the AI cache rides alongside, never instead. Every section degrades to a quiet line; a Roblox failure renders a stale-state note and still returns all local sections, with the name resolved from `alerted_games`/`watched_games`. |
| Scorecard | `scorecard.py` | Accountability read behind `/scorecard`: grades every game alerted in the last 72 h against the bot's own snapshot trail. Baseline = the game's latest snapshot **at or before** the alert timestamp (what the bot measured when it made the call — never re-derived from later data); latest = freshest snapshot. Verdicts: ✅ win (≥ +20% CCU), 🔕 quiet, 📉 miss (≤ −20%), ❔ unrateable (no usable baseline or latest) — unrateable calls are excluded from the aggregate hit-rate denominator so a wave of zero-baseline alerts can't fake a perfect record. Pure local math over `alerted_games` + `game_history`, zero Roblox requests. `collect_calls` is ONE query (two correlated subqueries per alerted game, both against the (game_id, timestamp) index) — the per-game loop it replaced opened 2 lookups per game every invocation, and `ledger.py` grades its weekly report through the same path. |
| Ledger | `ledger.py` | The accountability layer made continuous: a scheduler loop publishes the bot's own report card weekly (default Monday 13:00 UTC) to the alert channel. Grades the scorecard's alert calls (72 h window) AND the stored **AI verdicts** by stance — bullish (🟢 Worth Monitoring) correct when the game grew ≥ +20%, bearish (🟠 Risky / 🔴 Avoid) correct when it did not, neutral never graded — over the full 7-day week, only on games with a measurable outcome. Publish gating: due at/after the configured weekday+hour, dedup key = ISO year-week, key burned only after a successful send (failure retries next tick), catch-up lands in the same week, unresolved channel never burns anything. `LEDGER_ENABLED` / `LEDGER_WEEKDAY` / `LEDGER_HOUR_UTC` env knobs. Pure local math, zero Roblox requests. |
| AI analyst | `gemini_analyzer.py` | Multi-provider: Groq (`GROQ_API_KEY`, OpenAI-compatible, default model `llama-3.3-70b-versatile`) with Gemini (`GEMINI_API_KEY`) fallback; `AI_PROVIDER=auto|groq|gemini`. 24h per-game cache, daily quota gate, failures are diagnosed by cause and never cached. |
| AI scout channel | `ai_scout_channel.py` | Replies to any message in `AI_CHANNEL_ID` (legacy alias `AI_SCOUT_ID`); freeform questions + `@bot <universe_id>` analysis; per-channel conversation history in SQLite. |
| Persistence | `database.py`, `portfolio_db.py`, `sqlite_conn.py` | Single SQLite file (default `scoutbot.db`), WAL journal mode (a FILE property — set once at startup, never per connection), and one per-connection contract: `sqlite_conn.tune()` applies busy_timeout 30 s, `synchronous=NORMAL`, `temp_store=MEMORY` to EVERY module that opens the file — [database, portfolio_db, history, velocity, pulse, scorecard, ascent](Roblox-Game-Scout-Bot/) (hot paths) and the rare-path modules [gemini_analyzer, ai_scout_channel, growth, developer_intelligence, dossier, ledger](Roblox-Game-Scout-Bot/) (AI cache layer, per-message reads, user-triggered reads — single queries, bounded by design) all go through module-local `_connect()` helpers that stay individually test-monkeypatchable and apply the identical pragma set (pinned by `tests/test_conn_contract.py`). `{save_game_snapshots_bulk, update_watched_game_snapshots_bulk, record_game_snapshots_bulk}` write whole cycles in one transaction each; the single-game wrappers remain and are equivalent (pinned by tests). In-place ALTER TABLE migrations on startup. `save_game_snapshots_bulk()` writes a whole scan cycle's snapshots (~150 rows) in ONE transaction — the per-game commit path (~150 fsyncs/cycle) remains as the single-game wrapper. Bot tables (pulse reads the first four; writes nothing): `users` (per-user filter settings), `game_history` (indexed, pruned to 30 days on write), `chart_positions` (indexed, pruned to 30 days on write; `cycle_ts` separates scan cycles), `saved_games`, `alerted_games`, `scan_log`, `watched_games` (with a `source` column: `'user'` vs `'auto'`), `ignored_games`, `ai_analysis_cache`, `gemini_usage`, `ai_chat_history`, `developer_cache`, `ascent_state` (per-game radar cooldown state). `{save_game_snapshots_bulk, update_watched_game_snapshots_bulk}` write a whole cycle in one transaction each; the single-game wrappers remain and are equivalent (pinned by tests). In-place ALTER TABLE migrations on startup. |
| Portfolio stack | `portfolio_worker.py`, `portfolio_api.py`, `manage_portfolio.py` | FastAPI + 60s snapshot worker sharing the SQLite file; designed for one free Render service (`start.sh`). The worker writes its whole tick in ONE transaction (`record_game_snapshots_bulk` — it previously paid one connection + fsync per game after already batching the Roblox API calls; thumbnail warm-ups stay per-game by design, they only write when a game lacks a cached URL). Project stats derive from ONE series read (`_stats_from_rows`): the old builder cost ~7 connections per project (latest snapshot + 7d peak + four growth windows each re-reading the table); the list payload is now two bulk queries for ALL projects (`get_snapshots_bulk` + `get_latest_discord_snapshots_bulk`), and `/api/v1/health` finds which projects have data in one bulk latest-snapshot query. `GET /api/v1/leaderboard` serves the `/leaderboard` data as JSON (same store, same ordering, short-TTL cached, rate-limited 1–50 entries / ≤365 days) for external dashboards, with **ETag + 304 conditional requests**: the fingerprint covers only the ranking data, never `generated_at`, so an unchanged leaderboard between cache rebuilds still validates, and `Cache-Control: public, max-age=…` lets clients cache it directly. `GET /api/v1/series?ids=…&hours=…` serves up to 20 games' snapshot series in ONE indexed query (`get_snapshots_bulk`) with the same TTL cache + ETag/304 treatment — a dashboard used to cost one DB round-trip per chart; requested games with no data in the window keep an empty points list (gaps render, records don't 404). `/dashboard` renders the same cached payloads (`/api/v1/portfolio` + `/api/v1/leaderboard`) as plain server-side HTML with inline-SVG CCU sparklines (one bulk 24h series read) and auto-refreshes every 5 min via a meta tag; `/games` lists every alerted game from the leaderboard store with per-row 7d sparklines served by ONE bulk `game_history` query, and `/game/{id}` draws a game's 7-day CCU history from the bot's own `game_history` via the shared SQLite file plus a link to its JSON on `/api/v1/series` — all zero network, zero external assets, names escaped, explicit empty states — so the bot's own data is viewable without Framer. The scan pipeline's local reads carry a self-relative pytest guard (`tests/test_perf_guard.py`): both read paths are timed back-to-back on the same synthetic store, so the 2× bulk-vs-per-game floor cannot drift with hardware; it runs in CI on every suite run. |
| Web console | `web_ui.py`, `portfolio_api.py` | The server-rendered front door on the portfolio API: `/dashboard` (live market board — opportunity scores, fresh 24h movers, chart climbers, radar catches, latest alerts, portfolio cards), `/market` (market weather — 24h/7d breadth with fixed verdict thresholds, the median move, a fixed-bucket distribution of every fresh 24h move, leaders and laggards that never mix signs, the games furthest below their own 30d peak, per-chart footprint and each portfolio project's spread against the median; reads older than six hours are excluded rather than counted at an old price), `/games` (searchable/filterable index of every alerted, watched or portfolio game, with `/`-to-search and CSV export of the visible rows), `/compare` (head-to-head pickers, swap, at-a-glance metric table with the stronger value highlighted, and both games' 24h/7d/30d charts — each with the Scout-market median overlay; deep-linkable via `?a=&b=`), `/watchlist` (the tracking desk: every watched game with 14d trend, CCU, 24h/7d/since-watch growth, an honest Stale badge after six hours without a check, human-vs-auto watch labels, and client-side search/filter/sort over one bulk history read), `/scorecard` (the bot's own track record: every alert from the last 30 days graded at a fixed 72h horizon — raw win/quiet/miss spread, a score-vs-move calibration plot, hit rate and median move per score band, an explicit small-sample edge read, and every call's baseline, 72h read and latest reading; Open calls are excluded from the hit rate), `/game/{id}` (local dossier: a deterministic Scout read of 7-day direction, 30-day-peak position, 24h move and recorded signals with a stale-data override; 24h/7d/30d CCU charts with a dashed Scout-market median and a vs-market delta; alert record; call grade; chart positions; watch state; radar; cached AI verdict; and a newest-first signal timeline of its dated events — the benchmark is one cached bulk read shared by the game and compare pages, no LLM), and `/` → `/dashboard`. Zero external assets (one inline stylesheet + one inline script), zero Roblox requests: every number comes from `game_history`, `chart_positions`, `alerted_games`, `watched_games`, `ascent_state`, `ai_analysis_cache` and the portfolio tables. Data reads are bulk (one `game_history` query per section — movers, opportunity rows, index — never one per game), and each section degrades to an explicit empty state if its table is missing. Client-side search/filter/sort works on server-rendered rows, so the pages remain useful without JavaScript; all names, AI text and attributes are escaped. Forty-six page tests cover the redirect, market sections, market breadth/drawdowns/empties/escaping, the never-a-gainer-as-a-laggard rule, fixed verdict thresholds and half-open buckets, benchmark normalisation and its three-game floor, the game-page Scout read and stale override, the rendered overlay and vs-market delta, the thin-market empty case, timeline ordering and its empty state, index metadata, compare rendering/defaults/empties and its benchmark, watchlist rendering/empties/staleness/escaping, scorecard empties/grading/open calls/thresholds/escaping, detail rendering, window selection and escaping. |
| Rate limiting | `roblox_api_async.py` | All `games.roblox.com` traffic goes through a pacer (`ROBLOX_API_MIN_INTERVAL`, default 0.4 s + jitter) and retries 429/5xx with exponential backoff honouring `Retry-After`. A rejected batch chunk logs a WARNING naming the status — it used to be a DEBUG line, which is how a wrong 100-ID chunk size silently discarded every game in the chunk for months. That host throttles datacenter IPs far harder than residential ones; three per-game endpoints it used to call (`multigame-details` x2, `/v1/games/{id}/icon`) now 404 and were removed in favour of fields already present in the batch payload, and the Discord lookup no longer makes any request at all. |
| Local reads | `history.py`, `velocity.py`, `chart_rank.py` | The scan pipeline's per-cycle local reads are bulk: `growth_summaries_bulk()` and `compute_velocities_bulk()` answer every candidate's growth-over-window and 72h velocity in ONE indexed query each, and `chart_rank.attach_rank_signals_bulk()` attaches the whole cycle's chart signals in two indexed queries — replacing ~2 connections + 2 queries per charted game (benchmarked ~59x faster end-to-end on a 260-game store with ~215 charted). Single-game wrappers (`growth_summary`, `compute_velocity`, `attach_rank_signal`) share the same math and remain for commands that look up one game; equivalence is pinned by tests. Performance is guarded two ways: a self-relative back-to-back timing test (`tests/test_perf_guard.py`, 2× absolute floor) AND per-phase ratios committed in `tests/perf_baseline.json` by `scripts/bench_bulk_reads.py --record` — every phase must retain ≥25% of its committed speedup (growth/velocity/chart_rank ~124–191× at record time), so a bulk layer collapsing toward per-game work fails in CI, not on a live host months later. `_connect()` sets `PRAGMA synchronous=NORMAL` + `temp_store=MEMORY` per connection (WAL crash safety at a fraction of the fsync cost; sorts stay in memory). |
| Health & tooling | `health_check.py`, `validate_seeds.py`, `.github/workflows/ci.yml` | `health_check.py` probes every external dependency at startup (Roblox batch API, omni-search, Charts, AI key, Discord token) plus the local growth-history store, and backs the `/status` command. Nor does it drum up DB loops — each probe is best-effort, one shared HTTP session, and the outer-module sweep (tranche 8) verified the remaining background modules cost what they must: `embeds.py` is pure formatting with zero I/O; `ai_scout_channel.py` does one-or-two bounded reads per inbound message by design; `gemini_analyzer.py` pays no DB reads per item (24h per-game cache + daily quota gate), and `portfolio_worker.py`'s tick is now one transaction. CI (`.github/workflows/ci.yml`, root) runs the import smoke test + the full suite — including the baseline-pinned perf guard — on every push and PR. Each Roblox probe validates the response *payload* with a pure validator (`validate_games_payload`, `validate_omni_search_payload`, `validate_charts_payload`): an endpoint answering HTTP 200 with no usable data is a distinct ⚠️, not a healthy check. A 429 on `games.roblox.com` is retried and reported as a throttle warning, not an outage. `validate_seeds.py` verifies the curated seed list against the live API (`--prune` removes dead IDs). CI (`.github/workflows/ci.yml`, repo root) runs the import smoke test, the full suite with `pytest-cov` (`--cov-report=term-missing` in the log, `coverage.xml` uploaded as an artifact), and the baseline-pinned perf guard on every push and PR. |
| Rejection analytics | `filters.py` (`summarize_rejections`, `format_rejection_summary`) | When a scan matches nothing, the scanner and the scheduler log the dominant rejection category (e.g. `top reasons: Rating (257)`). ## Pipeline (scheduled scan)

```
collect_games_async ──> chart positions recorded (chart_positions)
        │                       │
        │               batch detail fetch ──> snapshot to game_history
        │                                            │
        │                    growth (last 2 snapshots) + trend + velocity
        │                          + chart-rank signal (rank, delta, best)
        │                                            │
        └──> enrich (ratings, thumbnail, description,
                    creator, Discord invite, tracked growth)
                                                     │
                              evaluate() — base + /settings profile
                                                     │
                                    filter FIRST, then AI (quota-safe)
                                                     │
                                  dedupe via alerted_games ──> embed + buttons
                                                     │
                                  auto-watch the alerted game (system row)
                                                     │
                                             run_tracker(bot)
```

## Deployment

- **Docker / Render:** see `Dockerfile`, `render.yaml`, `start.sh` (one free
  web service runs worker + API so both share the SQLite file).
- **Manual:** `python main.py` for the bot; `python portfolio_worker.py
  --interval 60` + `uvicorn portfolio_api:app` for the portfolio stack.
- Tests: `python -m pytest tests/` (offline; external APIs are mocked).

## Known deviations from the old PDF

1. Scheduler is `discord.ext.tasks`, not APScheduler/SQLAlchemy job store.
2. Trending source is the official Roblox Charts explore API, not RoTrends — and there is no third-party analytics dependency at all: growth history is computed from the bot's own 30-day snapshot store (`history.py`).
3. Schema matches `database.py` (this file), not the PDF's `games/users/watchlist/game_stats/analysis` draft.
4. Entrypoint is `main.py`; config lives in `config.py` + env vars, not `config.ini`.
5. AI provider is Groq-first with Gemini fallback; env names are `GROQ_API_KEY`/`GEMINI_API_KEY` (not `LLM_API_KEY`/`BOT_TOKEN`).
